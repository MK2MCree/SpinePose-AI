# 脊柱健康 Agent 融合蓝图

## 结论

当前项目已有“影像辅助分析 + 个人病例 + 趋势 + 报告”的底座。第一期不应再引入一个独立医疗影像系统，而应补齐个人侧的行为闭环：

```text
建立档案 → 版本化筛查/打卡 → 采集质量门控 → 已审核训练计划
      ↑                                            ↓
临床复查 / 影像记录 ← 周报与趋势 ← 动作执行与反馈 ← 实时训练
```

这是一个健康管理与辅助随访产品，而不是诊断系统。影像测算、体态记录、症状打卡和训练完成度必须在界面和数据模型上明确区分。

## 产品边界与分层

| 层级 | 面向谁 | 输出 | 不做什么 |
| --- | --- | --- | --- |
| 日常健康层 | 普通用户 | 采集质量、打卡、训练计划、完成情况、趋势 | 不诊断脊柱侧弯，不给出临床角度结论 |
| 复查协同层 | 有既往记录的用户与医生 | 医生录入的临床值、同方法纵向趋势、报告摘要 | 不用自拍替代 X 光或临床检查 |
| 专业评估层（后续） | 医师/科研人员 | 双机位动作任务、三维运动学原始结果、人工复核 | 不承诺消费级硬件可获得临床级数据 |

## 第一期开通的四项能力

### 1. 今日状态

- 极短打卡：疼痛、活动受限、久坐、睡眠、训练完成度与自由备注；
- 使用版本化问卷输出 `urgent_review / clinical_review / guided_plan` 三种**路由状态**；
- 页面只显示“下一步建议”和原因，不用疾病名称吓用户；
- 打卡永远允许跳过敏感项，并明确数据仅用于本人病例。

分诊规则不得散落在前端条件判断中。每次结果须保存 `triage_protocol_revision`、回答摘要和生成时间，后续由专业人员复核与升级。

### 2. 体态记录

流程固定为“说明 → 相机权限 → 站位轮廓引导 → 质量检查 → 覆盖层确认 → 保存记录”。

- 浏览器仅在用户点击后打开摄像头；
- 先检测单人、四个关键点、取景完整性、清晰度和姿态可见度；
- 质量不合格只提示重拍，不计算不对称指标；
- 合格后保存原始几何特征、采集方式、协议版本、质量分和叠加预览；
- 展示文案为“本次体态记录”“建议复测/咨询”，而不是“阳性、确诊、侧弯角度”。

同一趋势序列必须同时满足：视图相同、采集方法相同、协议版本相同、质量合格。不同条件的数据并列展示，但不连成一条趋势线。

### 3. 训练教练

训练内容只能来自经过专业审核的动作库。每个动作版本包含：适用条件、禁止条件、演示素材、摄像头视角、关键点规则、计数状态机参数、最大时长和停止条件。

会话状态：

```text
准备（权限/空间/姿态） → 校准（关键点质量） → 进行中
→ 暂停或完成 → 自主感受打分 → 写入病例 → 计划调整
```

计数不得以单帧命中作为一次动作。每个动作使用归一化评分的进入阈值和退出阈值构成滞回状态机，并记录低置信度帧占比。连续低质量时自动暂停计数并请求重新站位。

### 4. 周报与追踪

周报只汇总可解释的事实：打卡天数、训练完成次数/时长、每种记录的最新日期、同条件下的变化和待处理事项。

不得把“姿态不对称”与医生录入的 Cobb 角、X 光参数或疼痛评分混合为一个总分。总览可以并排展示，但每张卡都标注数据来源和含义。

## 数据设计

现有 `personal_case_entries` 适合继续保存时间线摘要：`checkin`、`video`、`clinical`、`rgb` 和 `dr`。为避免长期把复杂会话塞进 JSON，新增实体应独立建表并通过 `case_entry_id` 关联到时间线。

| 表 | 关键字段 | 约束 |
| --- | --- | --- |
| `triage_assessments` | user_id, protocol_revision, answers_json, route, created_at | 问卷版本不可覆盖；路由来源可审计 |
| `posture_captures` | user_id, case_entry_id, method, view, capture_protocol_revision, quality_json, metrics_json | 只有 quality=passed 的数据可进入可比趋势 |
| `rehab_plans` | user_id, source, plan_version, status, created_at | 只有审核动作可被激活；医生计划不可被 Agent 自动覆盖 |
| `rehab_sessions` | plan_id, exercise_id, exercise_version, quality_stats, repetitions, duration, self_report | 一个会话不可在完成后静默改写 |
| `exercise_catalog` | exercise_id, version, eligibility, contraindication, cue_rules, media_ref | 配置与代码解耦，临床审核后才发布 |

所有媒体默认本地即时处理；若用户选择保存，必须单独确认。姿态关键点和派生指标比原始视频更适合长期追踪。原始视频设短期保留期，并以用户可见的方式删除。

## API 与前端切入点

现有后端已经提供认证、`/api/personal-case`、记录新增/删除与本地 SQLite 病例隔离；前端已有个人病例趋势与状态打卡。因此融合应采用增量扩展，而不是替换现有工作台。

建议新增：

- `POST /api/agent/triage`：提交版本化问卷，返回路由状态；
- `POST /api/agent/posture-captures`：只接受已通过浏览器质量门控的结构化记录；
- `GET /api/agent/today`：合并待打卡、当前计划、上次记录和安全路由；
- `POST /api/agent/rehab-sessions`：以幂等 session token 保存训练结果；
- `GET /api/agent/weekly-summary`：服务端按数据来源分别汇总。

页面结构建议：

1. **今日**：唯一主操作是“完成今天的一步”，而非堆叠仪表盘；
2. **记录**：体态记录与影像记录分区，带方法/质量标签；
3. **训练**：卡片式计划、全屏专注训练、实时提示区、完成反馈；
4. **健康轨迹**：按来源筛选的趋势、周报和下次建议；
5. **专业复查**：仅展示医生录入与影像报告，视觉上与自测严格区分。

## 体验设计原则

- **低焦虑**：避免红绿灯式“疾病判定”；将状态表达为“可继续”“建议复测”“建议专业咨询”。
- **可解释**：每个数字都能展开看到数据来源、采集方式、质量与上一次比较的条件。
- **渐进呈现**：首次只需要资料、一个打卡和一个体态记录；训练计划在获得足够信息后才出现。
- **无障碍与容错**：文字提示不只依赖颜色；摄像头失败、网络失败、低性能设备都要有静态指引和手动记录退路。
- **可信而克制**：医疗免责声明不能只藏在页脚；在首次筛查、首次训练和报告导出时分别说明能力边界。

## 验收标准

1. 任一低质量采集不能生成可比较趋势或训练建议；
2. 任何需要复核/优先处理的路由都不能进入自动训练会话；
3. 所有趋势点可追溯到数据来源、协议版本和时间；
4. 连续置信度波动不会造成动作重复计数；
5. 同一训练会话重复提交不会双倍累计；
6. 个人病例、影像结果和训练记录始终按登录用户隔离；
7. 断网、拒绝摄像头、无模型、无关键点都能给出可恢复的下一步。

## 实施顺序

1. 先实现版本化打卡与 `Today` 页面，不接摄像头；
2. 再加入本地浏览器关键点采集、质量门控和“记录而非诊断”的体态页；
3. 接入 2–3 个经过审核的低风险训练动作，完成滞回计数、会话保存和周报；
4. 通过真实的非患者测试流程验证采集与数据隔离；
5. 在专业人员确认协议、动作库与分诊逻辑后，再扩大人群与功能；
6. 最后才评估 OpenCap 专业模式和独立的 X 光关键点研发。
