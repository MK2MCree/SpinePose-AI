# 脊柱健康 Agent：开源功能筛选清单

更新：2026-08-28。本文只用于决定做什么，不把研究原型包装成医疗能力。

## 先看结论

当前已在本机独立跑通两条可审计的算法链：RepDetect 的“33 关键点归一化 → 镜像不变两阶段 KNN → 置信度滞回计数”，以及 OpenCap 所依赖的“已标定多机位三角化 → 同步/重投影质量门”。它们均使用固定的合成样例和自动化测试；这不是把上游 Android 或 OpenSim 应用原样搬进来。

其余候选项目已经审计源码、许可证和用户流程，但受缺少专用数据、模型权重、运行时或许可证限制，尚未在本机跑完上游的端到端流程。因此它们是待选研发方向，而不是已交付功能。

| 候选 | 已确认功能 | 验证等级 | 建议决策 |
| --- | --- | --- | --- |
| **A. 日常训练与姿态记录**（基于 RepDetect 机制的自研 Web 模块） | 采集质量门控、关键点 KNN、训练计数、会话记录、同条件趋势 | **A：核心算法在本机 8 项测试通过** | **第一期应选** |
| B. RepDetect 原 Android App | 摄像头姿态、动作分类/计数、计划、历史、语音提示 | B：固定提交的核心源码已复现；未在本机构建 Android APK | 只提炼逻辑，不直接融合 App |
| C. OpenCap 专业动作评估 | 多机位视频转 3D 标记点、关节运动学 | B/C：标定三角化核心已验证；完整 OpenSim 运行时未满足 | 远期专业/科研模式 |
| D. X 光椎体关键点 | 椎体关键点、几何角度候选、叠加复核 | C：MIT 源码可读；旧依赖、数据和权重尚未验证 | 二期独立研发 |
| E. CT/MR 3D 分割 | 椎体、椎间盘等组织分割与三维预览 | C：Apache-2.0 源码/文档已审计；尚未安装模型与运行时 | 二期或三期异步专业服务 |
| F. 文献依据对话 | 结构化问诊、检索增强回答、红旗提醒 | C：流程已审计；上游仓库许可证/工程质量不宜直接使用 | 第一期间自研，不搬运源码 |

### 验证等级的含义

- **A**：本机有可执行代码和通过的自动化测试；可安全进入产品开发。
- **B**：上游功能、许可和代码入口清楚，但本机未跑通原项目全部运行时；只能作为机制来源。
- **C**：方向可靠，但仍受依赖、模型、数据或法律条件阻塞；不能承诺近期交付。

## A. 优先候选：日常训练与姿态记录

### 来源与已验证范围

- 机制来源：[RepDetect](https://github.com/giaongo/RepDetect)，Apache-2.0。
- 本项目没有复制 Android UI 或 Android 代码；独立的、可测试实现位于 `mindspine/independent_reproduction.py`，业务安全原型位于 `third_party_eval_20260828/proof_of_concept/spine_agent_logic.py`。
- 验证命令：

```powershell
& 'C:\Users\MK2SG\miniconda3\python.exe' -m pytest -q tests\test_independent_reproduction.py
```

- 已通过 8 项独立复现测试，覆盖 33 点嵌入的缩放/平移/镜像不变性、KNN 投票、完整动作周期、阈值边界、采集质量、相机同步、重投影误差和退化几何；原有业务原型另覆盖分诊阻断与趋势可比性。

### 用户能得到什么

1. 每日用极短问卷记录疼痛、活动限制、久坐、睡眠和备注；
2. 系统只给出“可进行已审核计划 / 建议咨询 / 优先处理”的下一步，不给疾病诊断；
3. 用户在浏览器完成一张体表姿态记录：前后/侧面站位、取景和关键点质量先检查；
4. 只有合格记录才进入个人趋势；用户能看到本次记录与上一次是否真的可比；
5. 在已审核的训练计划中完成动作；页面显示计数、暂停原因和完成情况；
6. 训练结束后反馈主观感受，系统生成周摘要和下一步。

### 完整用户流程

```text
登录
  → “今天”短打卡
  → 分诊路由
     ├─ 优先处理/建议复核：展示转介说明；训练入口锁定
     └─ 可继续：展示医生已审核的当日计划
          → 选择“姿态记录”或“开始训练”
          → 相机权限与站位引导
          → 单人、取景、关键点、清晰度质量检查
             ├─ 不通过：只提示重拍，不保存指标
             └─ 通过：确认叠加预览并保存记录
          → 全屏训练：校准 → 动作计数 → 暂停/完成
          → 主观感受反馈
          → 时间线、周报、同条件趋势
```

### 需要明确不做的事

- 自拍/摄像头只能反映体表姿态，不能计算或宣称临床 Cobb 角，不能诊断脊柱侧弯；
- 训练内容必须先由专业人员审核，Agent 不能根据一次自拍自行开具训练处方；
- 相机质量不合格、未知分诊结果或需复核状态，默认不允许进入训练；
- 原始视频不作为长期默认留存数据，优先留存经同意保存的关键点和派生指标。

### 与现有应用的融合点

现有 FastAPI 已有账户、个人病例时间线、RGB/DR/DICOM 导入、报告和趋势能力。新增 `triage_assessments`、`posture_captures`、`rehab_plans`、`rehab_sessions` 四类数据及 `/api/agent/*` 接口即可；不需要改写现有影像工作台。

### 筛选意见

**推荐选中。** 这是最小、最完整、用户每天真正会用的健康闭环，也是现有项目最缺的部分。

## B. 参考项目：RepDetect 原 Android App

### 它已有的功能

- 手机摄像头姿态关键点检测；
- 动作/瑜伽姿态分类，实时置信度反馈；
- 次数计数；
- 自定义训练计划；
- 本地历史、日/周汇总；
- 训练开始/结束语音提示和前后摄像头切换。

### 上游用户流程

```text
安装 APK → 选择动作（深蹲、俯卧撑、瑜伽等）
→ 设置目标次数 → 打开摄像头训练
→ 实时看次数/置信度 → 完成
→ 查看历史与日周汇总
```

### 为什么不直接并入

- Kotlin/Android/CameraX/ML Kit 与本项目的 FastAPI + Web 前端不是同一运行环境；
- 上游 Gradle 同时出现旧版与 beta 版依赖，直接构建风险高；
- 它面向通用健身，不包含脊柱分诊、影像边界、训练适用条件或隐私模型；
- 本机没有 Android SDK/adb，未把“核心算法已复现”误报成“APK 已构建”。

### 可取的部分

取“计划—训练—计数—历史”的闭环、平滑/滞回计数思想和低打扰的训练交互；在浏览器中使用许可清楚的关键点组件重新实现。

### 筛选意见

**不作为直接依赖，作为 A 的机制来源保留。**

## C. 专业候选：OpenCap 多机位三维动作评估

### 它已有的功能

- 两个或多个近同步视频；
- 相机标定、2D 姿态、三角化与 3D 标记点；
- OpenSim 关节运动学输出；
- 可进一步算运动动力学；
- 支持采集后本地重处理和科研数据复现。

### 上游用户流程

```text
用至少两部手机按采集规范录制同一动作
→ 上传/同步为一次采集会话
→ 后台执行姿态估计、三角化、OpenSim
→ 查看关节角度、三维轨迹和导出数据
→ 专业人员复核，作为康复评估或科研材料
```

### 当前复现条件

- [OpenCap Core](https://github.com/opencap-org/opencap-core)，Apache-2.0；源码固定到提交 `4c0aab5e2f1c80810585cda212769e9da4ec167e`；
- 需要 OpenSim、OpenPose/MMpose、FFmpeg、CUDA、同步视频与专用环境；
- 上游说明：最低 4GB CUDA 显存，常规 OpenPose 云端设置约 8GB，高分辨率约 24GB；
- 本机 RTX 4050 Laptop 为约 6GB 显存，且未安装 OpenSim/FFmpeg；因此没有端到端运行验证。
- 已独立验证的范围止于已标定标记点的三角化、时间同步和重投影质量门；没有把其误报为 OpenSim 关节角或临床结论。

### 与现有应用的正确融合方式

只能作为 Docker/独立 GPU worker：主应用提交任务、轮询状态、展示预览和复核结论。绝不可把它与现有 FastAPI 进程和普通用户相机采集混为一个功能。

### 筛选意见

**暂不选。** 它有价值，但不适合第一期普通用户体验，也超过当前硬件条件。

## D. 专业候选：X 光椎体关键点与角度候选

### 它已有的功能

- [Vertebra Landmark Detection](https://github.com/yijingru/Vertebra-Landmark-Detection)，MIT；
- 输入正位脊柱 X 光，输出椎体相关关键点；
- 后续可由独立几何模块形成“角度候选”和 X 光覆盖层，供人工检查。

### 目标用户流程

```text
专业用户上传授权的正位 X 光 / DICOM
→ 系统校验图像类型、方向和清晰度
→ 异步提取椎体关键点
→ 在原图上显示关键点与候选线
→ 医师调整/确认关键点和测量值
→ 保存“算法版本 + 人工复核状态 + 最终值”到病例
```

### 当前限制

- 代码许可是 MIT，但依赖 Python 3.6 / PyTorch 1.1，和项目当前 PyTorch 2.10 不兼容；
- 预训练权重从外部链接下载，训练数据来自外部数据集，均需单独审查下载许可与用途；
- 还没有用合法样本完成本机推理和临床一致性验证。

### 筛选意见

**可选为第二期研发，不得作为第一期的自动诊断功能。** 若选中，先做“上传—覆盖层—医生复核—可审计保存”，再谈自动量化。

## E. 专业候选：CT/MR 三维分割

### 它已有的功能

- [TotalSegmentator](https://github.com/wasserth/TotalSegmentator)，Apache-2.0；
- 接收 NIfTI 或一个检查的 DICOM 切片目录；
- 支持 CT/MR，并提供 C1–L5、椎间盘、椎体等分割任务；
- 可输出掩膜、预览和体积等统计。

### 目标用户流程

```text
专业用户上传已脱敏的 CT/MR 检查
→ 系统校验完整性与格式，排入后台队列
→ 独立 GPU/CPU worker 运行分割
→ 在切片和三维预览中显示掩膜
→ 专业人员确认/标注异常或驳回结果
→ 导出研究报告或保存为专业影像记录
```

### 当前限制

- 当前环境有 PyTorch、OpenCV、NIfTI 读取能力，但未安装 TotalSegmentator、其模型权重和完整影像运行时；
- 项目说明明确：它不是医疗器械，不面向临床使用；
- 计算量与隐私级别远高于日常自拍，必须异步化、隔离存储和人工复核。

### 筛选意见

**可选为第二/三期专业入口。** 对已有 DICOM/X 光工作台是增量能力，但不应抢占第一期的用户价值。

## F. 对话候选：脊柱/腰背健康问答 Agent

### 参考功能

- [Back Pain RAG Chatbot](https://github.com/MouadBhih/BACK_PAIN_RAG_CHATBOT) 的流程是 PDF 文献切分 → 向量检索 → 基于检索内容回答 → 红旗提示；
- [PhysioGPT](https://github.com/Mayank-bhardwaj02/PhysioGPT) 展示了结构化问诊 → 个性化运动建议的交互。

### 我们应提供的用户流程

```text
用户描述问题
→ Agent 先做最少量的结构化追问
→ 红旗规则优先判定
   ├─ 需要优先处理：清晰说明为何应尽快寻求专业帮助；不生成训练动作
   └─ 非优先处理：仅基于已审核知识库给出生活方式/记录建议
→ 回答展示来源、适用范围和未知信息
→ 用户可进入打卡、体态记录或“联系专业人员”
```

### 必须修正的上游问题

- Back Pain RAG Chatbot 的 README 写 MIT，但仓库没有独立 LICENSE 文件，因此不复制 notebook；
- PhysioGPT 没有许可证，且源码使用全局会话状态，可能串用户，也开启危险的向量库反序列化选项；
- 任何对话模块都不能诊断、开药或自动生成未审核训练处方；必须在中文场景建立版本化红旗规则、可见来源和会话隔离。

### 筛选意见

**推荐与 A 一起选中，但按自研实现。** 它负责把分散的影像、记录和训练入口串成一个真正的 Agent。

## 建议筛选组合

| 组合 | 包含 | 给用户的核心价值 | 成本与风险 |
| --- | --- | --- | --- |
| **推荐：健康闭环版** | A + F | 每天能用：问答分流、记录、训练、趋势 | 中等；可在现有应用增量开发 |
| 影像协同版 | 推荐组合 + D | 让医师复核 X 光时有关键点覆盖和审计链路 | 高；需要合法数据、模型迁移和专业验证 |
| 专业三维版 | 影像协同版 + E + C | 服务专业机构/科研的 CT、MR、三维动作评估 | 很高；需独立计算与合规体系 |

## 本次筛选后的建议

先选择“健康闭环版”。具体首批交付依次是：

1. 中文结构化对话和红旗分流；
2. `Today` 页面与版本化打卡；
3. 浏览器姿态记录的质量门控；
4. 两到三个经审核的低风险训练动作、滞回计数与会话保存；
5. 按数据来源分开的周报和个人轨迹。

选中 D、E、C 前，必须先准备合法的样本、专家验收规则、模型/数据许可证清单和独立运行环境。
